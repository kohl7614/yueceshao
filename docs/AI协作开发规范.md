# AI 协作开发规范（AI 写码 · AI 预审 · 人终审）

> 参考来源：Anthropic Claude Code 团队公开的 AI 编码工作流最佳实践，结合本团队实测（PR #6 首次完整走通"队员+AI 写码 → AI 预审 → 负责人终审合并"）整理。
> 与其他文档的分工：`README.md`＝红线与编码规范；`docs/协作规范.md`＝git 流程；`开发手册`＝模块任务与验收标准；**本规范＝人与 AI 协作写代码的质量流程**。

## 1 核心循环

```text
[计划先行] AI先出设计要点 → 负责人批准计划
      ↓
[TDD实现] 关键路径先写测试看它红 → 再实现看它绿
      ↓
[自查+PR] 按PR模板发PR（做了什么/怎么测/红线自查/AI参与声明）
      ↓
[AI预审] 独立上下文的AI实例按清单审PR，意见写入PR评论
      ↓
[人终审] 负责人看AI意见+亲自看diff → squash合并 → 删分支
      ↓
[CI兜底] GitHub Actions 自动跑 pytest，红=不算完成
```

**铁律：永不盲并。** AI 写的代码"看起来对"和"对"是两回事——无论谁写的 PR（人/ AI/ 人+AI），未经审查不得合并。

## 2 计划先行（超过 200 行的 PR）

Anthropic 团队最重要的经验：**改代码之前先改计划**。计划批错成本是分钟级，代码审错成本是小时级。

- 触发条件：预计 diff >200 行，或引入新数据结构/新依赖/新接口；
- 计划内容（写在 issue 或 PR 草稿里，五行以内）：要动哪些文件、核心数据结构、对外接口、测试方案；
- 负责人回复"计划 OK"后才开写。开发手册§3 的 PR 表格已预先固定了各 PR 的骨架，视同计划已批。

## 3 TDD：四个关键路径必须"先红后绿"

以下四类是引用零容错的地基，**必须先写测试、亲眼看它失败、再实现、看它变绿**（其余 PR 至少附带测试即可）：

| 关键路径 | 对应模块 | 为什么不能错 |
|---|---|---|
| 分块对齐（条款号↔chunk一一对应） | rag/chunker | 错位=引用错误率指标崩塌 |
| 时效硬过滤 | rag/retriever | 漏过滤=误引已失效条款 |
| 引用校验器 | gen/validator | 它是幻觉的最后防线 |
| 规则命中 | rules/engine | 误报/漏报直接进报告②段 |

## 4 PR 描述模板（`.github/PULL_REQUEST_TEMPLATE.md` 已配置）

发 PR 时 GitHub 会自动带出六栏模板，**全部填写**再请求审查：

1. **做了什么**（对应开发手册哪个 PR 编号）；
2. **为什么这样做**（关键取舍一句话）；
3. **怎么测的**（pytest 结果、本地验收输出）；
4. **红线自查**（六条红线逐条 ✅/不适用）；
5. **输出样例**（命令行截图或文本，demo 类 PR 必附页面截图）；
6. **AI 参与声明**（谁写的：人 / AI工具名 / 人+AI）。

## 5 AI 预审 + 人终审（双保险）

Anthropic 的实测结论：**换一个全新上下文的 AI 实例审 PR，能发现疲劳的人眼和写码的 AI 自己都漏掉的问题**。我们的落地：

- **AI 预审**：负责人把 PR 交给一个独立 AI 会话（非写码的那个），按固定清单审查并把结论写成 PR 评论——清单=六条红线＋编码规范＋测试覆盖＋边界条件＋与开发手册验收标准逐条比对；
- **人终审**：负责人（杨宇翔）最后亲自过 Files changed，重点看 AI 意见中标记的风险点；AI 意见是参考不是免检通行证；
- AI 预审者**不合并**——合并权只在负责人，与仓库保护机制一致。

## 6 CI 兜底（`.github/workflows/ci.yml` 已配置）

- 每个 PR 自动：装依赖（若存在 requirements.txt）→ 跑 pytest（若存在测试）；
- **CI 红=不许请求审查**，先把测试修绿；
- 这条把开发手册"PR 必附 pytest"从自觉变成机制。

## 7 会话纪律（AI 使用的三条习惯）

1. **一个任务一个会话**：上下文不跨任务复用——写码会话里积累的假设会把下一个任务带偏；任务切换就开新会话（对应 Claude Code 的 /clear 习惯）；
2. **检查点交付**：长任务（如一次开发两个 PR）在中途检查点停下等指令，不一口气跑完；
3. **AI 参与透明化**：AI 编写/参与编写的 PR 打 `ai-authored` 标签——不伪装纯手写，也便于事后统计 AI 协作的实际质量（答辩时是加分的工程化素材）。

## 8 我们现阶段不采用的（防止过度工程）

| 做法 | 不采用理由 |
|---|---|
| CI 容器里跑自主 agent（跳权限自动修 PR） | 测试量还少、信任未建立；等测试套件成型后再议 |
| Slack/GitHub 深度通知集成 | 微信＋GitHub Watch 已够用 |
| AI 自动合并小 PR | 合并权集中是本项目协作基石，不自动化 |
